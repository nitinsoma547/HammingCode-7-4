# Meta Graph API — operator setup

How to wire The Business to post directly to Facebook Pages + Instagram
Business accounts using `api/src/services/meta/`. Replaces (or
complements) Outstand for content publishing.

**Timeline reality:** the code is ready today. Meta's gate (App Review
for content-publishing permissions) takes **4–6 weeks** in May 2026 per
Meta's current docs. Start the registration now if Saturday's pitch
includes "we own our own posting infrastructure."

---

## 1. What each client needs (pre-wiring)

Per client, before we can post on their behalf:

1. A **Facebook Page** they own. (Not a personal profile.)
2. An **Instagram Business or Creator account** linked to that Page.
3. Make us an Admin on the Page (Meta Business Manager > Page Roles).

That's it. The Meta App + tokens live on our side.

---

## 2. Register the Meta App (one time, our side)

1. Create a Meta Business account at <https://business.facebook.com>.
2. Go to <https://developers.facebook.com/apps> and create a new app:
   - Use case: **Other**
   - Type: **Business**
   - Name: "The Business — Marketing" (or our final brand)
3. In the app dashboard, add products:
   - **Facebook Login for Business** — needed for the access token flow
   - **Instagram Graph API**
   - **Pages API**
4. Add Privacy Policy URL, Terms of Service URL, Data Deletion URL,
   App Icon. These are App Review prerequisites.

---

## 3. Request permissions (App Review)

Submit for review with this exact permission set — anything more triggers
a "request unnecessary permissions" rejection:

| Permission                       | Why we need it (use case copy)                                 |
|----------------------------------|-----------------------------------------------------------------|
| `pages_manage_posts`             | Schedule and publish posts to client Facebook Pages on the monthly calendar generated by our content team. |
| `pages_read_engagement`          | Read engagement metrics on our scheduled posts for monthly client reports. |
| `instagram_basic`                | Identify the client's Instagram Business account linked to the FB Page. |
| `instagram_content_publish`      | Publish photos, videos, and Reels to client Instagram Business accounts on the monthly calendar. |
| `instagram_manage_comments`      | (Optional, v2) Respond to comments on behalf of clients with operator approval. Skip for v1. |
| `pages_show_list`                | List the Pages the client has admin access to during onboarding. |

For each permission, submit:
- A **screencast** showing the flow end-to-end. Reviewers want to see:
  the operator picks a client → the system reads brand_profile + month →
  generates the post (we show the JSON output) → operator approves →
  the post hits the page.
- A **plain-English use case** copy. Use the table above.

**Common rejection reasons** (per Meta docs May 2026):
- Vague privacy policy. Use a real one with specifics on what we store.
- No screencast. They WILL reject.
- Asking for permissions we don't use. Skip `instagram_manage_messages`,
  `pages_messaging`, etc., for v1.

## 4. Generate the long-lived Page Access Token

Once App Review approves:

1. In Graph API Explorer (<https://developers.facebook.com/tools/explorer>),
   select the app and the client's Page.
2. Get a **short-lived user access token** with the approved scopes.
3. Exchange for a **long-lived user token** (60 days):
   ```
   GET /oauth/access_token
     ?grant_type=fb_exchange_token
     &client_id={app-id}
     &client_secret={app-secret}
     &fb_exchange_token={short-lived-token}
   ```
4. Use the long-lived user token to get a **long-lived Page access
   token** (never expires unless revoked):
   ```
   GET /{user-id}/accounts?access_token={long-lived-user-token}
   ```
   The response includes `access_token` per Page. That's the value
   for `META_PAGE_ACCESS_TOKEN`.

Also grab the **Instagram Business Account ID** linked to the Page:
```
GET /{page-id}?fields=instagram_business_account&access_token={page-token}
```
The `instagram_business_account.id` is `META_IG_USER_ID`.

## 5. Populate `.env`

```bash
META_PAGE_ACCESS_TOKEN=<long-lived page token>
META_FB_PAGE_ID=<page id>
META_IG_USER_ID=<ig business account id>
META_GRAPH_API_VERSION=v21.0
```

## 6. Smoke test

From `api/`:

```bash
npm install
npm run test:meta-post              # dry-run, no network calls
DRY_RUN=false npm run test:meta-post  # hits Meta for real
```

The script posts a text message to the Page + a photo to IG. Use a
**test Page** you own — not a real client Page — until the flow is
proven.

---

## 7. Per-client token storage (production)

`META_PAGE_ACCESS_TOKEN` in `.env` is fine for dev / a single test
client. For multi-client production, store tokens in the `clients`
table (Supabase) — one row per client with `meta_page_id`,
`meta_ig_user_id`, `meta_page_access_token`. The campaign-generator
reads per-client tokens at run time.

**Token rotation:** Page access tokens *can* expire if:
- Operator account password changes (revokes derived tokens)
- Client removes our Page Admin role
- Meta revokes for ToS violations

Add a background job that pings `/me?access_token=...` per client
weekly. If 401, surface to the operator to re-OAuth.

---

## 8. Rate limits

Meta caps **200 API calls per hour per unique IG account** in a
rolling window. With our cadence (12 posts/month + 4 GBP + ~30 reads
for analytics) we're well under. Keep a per-client call counter
in `campaigns.total_meta_calls` for visibility.

---

## 9. Fallback path

While App Review is pending (4-6 weeks):
- Use Outstand for posting (`api/src/services/outstand/`)
- Our content team continues to produce the same JSON shape
- Once approved, swap the scheduler from Outstand to our Meta client
  per-client — no content regeneration needed

The `social-media-planner` output JSON shape is the same either way.
